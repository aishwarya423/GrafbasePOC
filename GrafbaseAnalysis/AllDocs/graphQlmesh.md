## What is GraphQL Mesh?

**GraphQL Mesh** is an open-source tool from **The Guild** that **turns non-GraphQL sources (REST, gRPC, SOAP, OpenAPI, Postgres, MongoDB, etc.) into a unified GraphQL API**.

You point it at your REST APIs (or OpenAPI specs), and it auto-generates a GraphQL schema and resolvers. No hand-written subgraphs needed.

```
                Mesh reads OpenAPI specs and auto-generates everything
                ↓
GraphQL Client → GraphQL Mesh → REST APIs
                  ├── Schema autogenerated from OpenAPI
                  ├── Resolvers autogenerated
                  ├── Caching built-in (in-memory or Redis)
                  └── Federation, transforms, auth all configurable
```

It's essentially **"Grafbase Gateway + Apollo Subgraphs + Caching, all rolled into one OSS tool."**

## Does Mesh replace a step in our workflow?

**Yes — it collapses multiple steps into one.**

### Current workflow (Grafbase approach)
1. Define REST APIs in OpenAPI ✅ (you have this in `docs/`)
2. Hand-write 3 GraphQL subgraph SDL files (`schemas/*.graphql`)
3. Hand-write resolvers in `subgraph-server/server.js`
4. Run `compose-supergraph.js` to merge SDLs into supergraph
5. Configure Grafbase Gateway in `grafbase.toml`
6. (For persistent cache) Get Enterprise license + activate Redis backend

### Mesh workflow
1. Define REST APIs in OpenAPI ✅ (same)
2. Write a single `.meshrc.yaml` pointing at the OpenAPI specs
3. Run Mesh — done

That's it. No hand-written resolvers, no schema composition step, no license, **persistent caching is OSS**.

  redis:
    host: valkey
    port: 6379

# Per-field TTL caching

  - targetTypeName: Query
    targetFieldName: account

      ttl: 300

## Where Mesh is weaker than Grafbase

It's not all upside — Mesh has trade-offs:

### 1. Performance
- Mesh runs on **Node.js** — slower than Grafbase's **Rust** runtime
- For low-traffic POCs / dev: doesn't matter
- For high-traffic production: Grafbase Enterprise wins on raw throughput

### 2. Caching granularity
- Mesh caches **resolver outputs** by argument hash
- Grafbase Enterprise caches **federation entities** with auto-tagging across the entire graph
- For multi-query entity reuse, Grafbase's model is more efficient

### 3. Federation maturity
- Mesh supports Apollo Federation but it's not as battle-tested as Apollo's own gateway or Grafbase
- Edge cases (entity resolution across many subgraphs, complex `@key` patterns) are smoother in Grafbase

### 4. Strategic risk
- The Guild is a smaller company than the Apollo or Grafbase ecosystems
- Mesh's release cadence slowed in 2024–2025 (v1 is stable but v2 has been in development for a while)
- If you're betting on a long-lived stack, Grafbase + Apollo has more momentum

### 5. Less observability tooling
- Grafbase Enterprise has built-in metrics, dashboards, OTLP exports
- Mesh has plugins for this but you wire them yourself

## When should you choose Mesh over Grafbase?

### Choose Mesh when:
✅ Your data sources are REST/OpenAPI/SOAP/Postgres — Mesh auto-generates the GraphQL layer
✅ You want persistent caching but can't / don't want to pay for Grafbase Enterprise
✅ You want minimal code — config-only setup is the goal
✅ Schema transforms (renaming, filtering, prefixing) are important to you
✅ This is a POC or low-to-medium traffic production app
✅ You're already a Node.js shop

### Choose Grafbase when:
✅ You're already paying for Enterprise (best-in-class federation runtime)
✅ Performance is critical (Rust runtime > Node)
✅ You need cutting-edge federation features (entity tagging, partial cache invalidation)
✅ Strong observability/SaaS tooling matters

### Choose neither (stay with current Apollo) when:
✅ You want the most mature federation ecosystem with the largest community
✅ You don't mind writing subgraphs by hand
